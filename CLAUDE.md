## Fixes / TODO

### Fixed (2026-09-15)

Reproduced the failing build for real with `Videodromm\VDRUIProject\vc2026\VDRUIProject.sln` (VS2026 / MSBuild `v145` toolset, x64) and iterated until both Debug and Release link cleanly end to end (Cinder core + the generated app). Root causes and fixes, in the order they were uncovered:

1. **`#error: WinSock.h has already been included`** (item 1 below, project generation/build) — root cause: nearly every header in `Cinder-VDR/include` and `Cinder-VDRUI/include` starts with `#include "cinder/app/App.h"`, which (on `CINDER_MSW_DESKTOP`) transitively includes `cinder/msw/CinderMsw.h`, which does a bare `#include <windows.h>` with no `WIN32_LEAN_AND_MEAN` guard (Cinder core, not touched). That pulls in the legacy `<winsock.h>`. Later in the same translation unit, `VDSession.h` includes Cinder-HTTP's `cinder/http/http.hpp`, which pulls in the real standalone `asio/asio.hpp` (`Cinder/include/asio`) — `asio/detail/socket_types.hpp` then hard-errors because `<winsock.h>` beat it to the punch. There is no XML hook in the `cinderblock.xml`/`template.xml` schema to inject a project-wide preprocessor definition (confirmed: no block or template anywhere in `Cinder/blocks` uses one), so the fix had to be code-level: every header in `Cinder-VDR/include` and `Cinder-VDRUI/include` that includes `cinder/app/App.h` now defines `WIN32_LEAN_AND_MEAN` immediately before that include (guarded, `_WIN32` only). This is future-proof for new headers only if they follow the same convention — copy the guard when adding a new `.h` that includes `cinder/app/App.h`.
2. **Boost/asio breakage in Cinder-WebSocketPP** (item 2 below) — three separate bugs, all in `Cinder-WebSocketPP/src/WebSocketConnection.h` and `.../src/websocketpp/common/asio.hpp` (vendored websocketpp source, editable per Goals):
   - MSVC never sets `__cplusplus` to the real standard version unless `/Zc:__cplusplus` is passed (it wasn't), so websocketpp's own C++11 auto-detect (`websocketpp/common/cpp11.hpp`, `__cplusplus >= 201103L`) never fires. Someone had already worked around this before by manually defining the individual `_WEBSOCKETPP_CPP11_*` feature macros in `WebSocketConnection.h`, but `_WEBSOCKETPP_CPP11_TYPE_TRAITS_` was missing, so `websocketpp/common/type_traits.hpp` fell back to `#include <boost/aligned_storage.hpp>` — gone, since boost was removed. Added the missing define.
   - `WebSocketConnection.h` includes `asio/asio.hpp` directly without ever defining `ASIO_STANDALONE`, so `websocketpp/common/asio.hpp` fell back to its boost branch (`<boost/asio.hpp>`, `<boost/version.hpp>`) instead of the already-standalone-aware branch it has (websocketpp itself fully supports `ASIO_STANDALONE`, same as Cinder-HTTP's `http.hpp`). Added `#define ASIO_STANDALONE 1` before the include, matching `http.hpp`'s convention.
   - Once both of the above are fixed, `websocketpp/common/asio.hpp`'s own compat shim (`namespace asio { struct io_service : io_context {...}; }`, added for standalone-Asio >= 1.13) collides with `asio/io_service.hpp` (`typedef io_context io_service;`, unconditionally present because Cinder's bundled Asio 1.18.1 never defines `ASIO_NO_DEPRECATED`) — `error C2371: 'asio::io_service': redéfinition; types de base différents`. Cinder's Asio already keeps every deprecated `io_context` member (`post`/`dispatch`/`reset`/nested `strand`/`work`) that the shim exists to backport, so the shim is redundant here. Guarded it with an added `&& defined(ASIO_NO_DEPRECATED)` so it only compiles for Asio builds that actually need it.
   - Also found and fixed two genuine bugs while in `cinderblock.xml` for VDR/VDRUI: both blocks had a `<requires>` on their *own* block id (`Cinder-VDR` requiring `com.videodromm.vdr`, `Cinder-VDRUI` requiring `com.videodromm.vdrui`) — self-dependencies, almost certainly copy/paste artifacts, removed. `Cinder-VDR`'s `cinderblock.xml` also had `<requires>org.libcinder.HTTPS</requires>` listed twice; de-duplicated.
   - (`Cinder-WebSocketPP/compat/include/asio` and `cinderblock.xml.tochack`, both untracked, look like an earlier, abandoned attempt at this exact fix using a vendored second copy of Asio at the wrong include path — left untouched/unused; the fix above uses Cinder's own already-globally-available Asio instead, avoiding a second-copy version-mismatch risk entirely.)
3. **Cinder-HTTP `http.hpp`/`connector.hpp`/`handshaker.hpp`/`requester.hpp`/`responder.hpp` used a removed Asio/Cinder API** — surfaced only once #1 and #2 stopped masking it: `ci::app::App::get()->io_service()` doesn't exist any more (renamed `io_context()` in current Cinder `AppBase.h`), and `asio::ip::tcp::socket::get_io_service()` doesn't exist any more in Asio 1.18 (sockets are executor-based now). Fixed by calling `App::get()->io_context()` once (in `http.hpp`'s `Session`/`SslSession` constructors) and, everywhere else, replacing `<socket>.get_io_service()` with `mSession->get_io_service()` (the accessor `http.hpp` already provides on `Session`/`SslSession`) — same underlying `io_context`, no behavior change.
4. **Stale `ui::Shutdown();` call** in `Cinder-VDRUI/templates/VDRUI/src/_TBOX_PREFIX_App.cpp` (and the already-generated `Videodromm\VDRUIProject\src\VDRUIProjectApp.cpp`) — leftover from an older ImGui integration; current Cinder's `cinder/CinderImGui.h` only exposes `ImGui::Initialize()` (already called), no `Shutdown()`/`ui` namespace, and doesn't need one (ImGui's context is torn down automatically). Removed the call from both the template and the generated project.
5. **"remaining json compilation problems"** (item 3 below) — `Cinder/src/cinder/JsonTree.cpp` exists on disk but was never added to `Cinder/proj/vc2026/cinder.vcxproj` (nor `vc2019/cinder.vcxproj` — pre-existing gap in both, not a vc2026-migration regression). Only `Json.cpp` was compiled into `cinder.lib`, so anything calling `JsonTree::JsonTree()`, `::write()`, `::addChild()`, `::pushBack()`, `::serialize()`, `::makeArray()`, `WriteOptions::WriteOptions()`, etc. (basically all of `VDSettings`, `VDAnimation`, `VDMix`, `VDMidi`, `VDMediator`, `VDWebsocket`, `VDSessionFacade`, `Warp`/`WarpBilinear`/`WarpPerspectiveBilinear`) compiled fine but failed at link with `LNK2001/LNK2019` unresolved externals. Added `JsonTree.cpp` to `cinder.vcxproj`/`.vcxproj.filters` (vc2026) next to `Json.cpp`, then rebuilt `cinder.lib` for both Debug and Release x64 — this is an edit to Cinder's own **project file**, not its framework source, so it doesn't conflict with "Cinder shouldn't be modified" above; the prebuilt `Cinder\lib\msw\x64\{Debug,Release}\v145\cinder.lib` now needs a rebuild any time `Cinder/proj/vc2026/cinder.sln` changes.

Verified by building `Videodromm\VDRUIProject\vc2026\VDRUIProject.sln` for Debug|x64 and Release|x64 end to end (MSBuild, real compiler run, not a guess) — both now produce `VDRUIProject.exe` with zero errors. Launching the built exe to smoke-test at runtime (window opening, folder/shader browser hitting a live server, warp/mixette rendering) was attempted but the automated environment this fix was done in refuses to launch a new GUI process ("Accès refusé" from both a background shell launch and `Start-Process`) — an environment/sandbox restriction, not something about the app. Run `Videodromm\VDRUIProject\vc2026\x64\{Debug,Release}\VDRUIProject.exe` locally to confirm it actually opens and renders before calling VDR/VDRUI "done" on Windows.

### Fixed (2026-09-16, VDSession HTTP callback crash when the folder/shader API is unreachable)

Reported: hitting the `onError` breakpoint in `VDSession::makeFolderListRequest` (`Cinder-VDR/src/VDSession.cpp`) when the folder/shader browser API's `localhost` server is unreachable, then continuing, crashes the app — Debug only, never in Release. Visual Studio's own diagnosis (locals + call stack, saved to `apicrash.txt`): `abort()`/`terminate()` called directly from inside the `onError` lambda body (`VDSession.cpp:188`, the `CI_LOG_E(ec.message() << ... << url->to_string())` line), reached via `asio::asio_handler_invoke` → `cinder::http::Session::onError` → the lambda, with `url` confirmed valid (`protocol_="http"`, `host_="localhost"`, 3 strong refs, not null/corrupt). The reported "Stack overflow" + "Access violation writing to 0x60000" are secondary: MSVC's Debug CRT abort() teardown (`_VCrtDbgReportW`) produces that exact exception pair when unwinding an exhausted/already-terminating thread — they are not evidence of real runaway recursion (the captured call stack is only 4-5 frames deep, far too shallow for that), and Release never shows them because Release skips the CRT instrumentation that triggers this path.

Defensively wrapped all 8 `onComplete`/`onError` lambdas in `VDSession.cpp` (all four request/response handler pairs: `makeRequest`/`makeFolderListRequest`/`makeShaderListRequest`/`makeShaderContentRequest`) in `try { ... } catch (const std::exception&) { ... } catch (...) { ... }`, logging failures via `app::console()` instead of `CI_LOG_E`. This is correct and stayed in — `asio::io_context::poll()` (pumped every frame from `AppBase::privateUpdate__`, `Cinder/src/cinder/app/AppBase.cpp:232`) has no exception safety net around user handler dispatch, so nothing should ever throw out of these lambdas regardless of cause — **but it did not stop the crash**: reproduced again afterward with the exact same `abort()`/CRT-report signature, just surfacing from a different function (`makeShaderContentRequest` this time). That one fact is what cracked the real bug open: a real C++ exception *would* have been caught by the new try/catch, so whatever this is, it bypasses C++ exception handling entirely — ruling out "an exception is thrown" as the mechanism altogether, regardless of which expression.

**Actual root cause**: undefined behavior in `<cctype>` calls (`std::tolower`, `std::isdigit`, `std::isalnum`) throughout `Cinder-HTTP/src/cinder/http/url.ipp` (`Url::set_protocol`, `Url::from_string`'s protocol-lowercasing and port-digit-validation loops, and `Url::unescape_path`) and `Cinder-HTTP/src/cinder/http/parsers.hpp` (`tolower_compare`, used for HTTP header name comparisons). Every one of these passed a plain `char` (signed on MSVC) directly to a `<cctype>` function. Per the C standard, the argument to these functions must be representable as `unsigned char` or equal to `EOF` — any byte with the high bit set (i.e. any non-ASCII byte, such as an accented character in a folder or shader filename) sign-extends to a negative `int` when `char` is signed, which is undefined behavior. MSVC's Debug CRT implementation of `<cctype>` actually asserts on this out-of-range input and calls straight into its fault-report/`abort()` path (`_VCrtDbgReportW`) — **not** a thrown C++ exception, so no `try`/`catch` anywhere can intercept it; Release's CRT has no such assert, so it silently misbehaves instead of crashing, matching the observed Debug-only behavior exactly. `Url::unescape_path` (called from `Url::from_string` while parsing the path component of every request URL built in `VDSession.cpp`, e.g. `api/folders/<folder>/<extension>/<name>`) is the one most likely to actually fire in practice, since folder/shader names are user-facing filenames that can contain non-ASCII bytes — this also fits the reporter's environment being French-localized (crash text was in French), where accented filenames are common.

Fixed by casting every such argument to `unsigned char` before the `<cctype>` call, at all 5 sites (`url.ipp` ×4, `parsers.hpp` ×1) — the standard, textbook fix for this exact class of bug. The try/catch wrapping from the first pass was left in place as defense-in-depth (it's still correct practice for this callback boundary, it just wasn't the fix for *this* bug). Verified by rebuilding `Videodromm\VDRUIProject\vc2026\VDRUIProject.sln` Debug|x64 end to end (MSBuild, real compiler run, full rebuild since a shared header changed) — zero errors, links clean.

Not verified at runtime (same GUI-launch restriction noted elsewhere in this file) — run `VDRUIProject.exe` locally, in particular exercising the folder/shader browser against folder or shader filenames containing accented/non-ASCII characters, to confirm the crash is actually gone and not just moved again.

**Update**: the `<cctype>` fix above was real and worth keeping, but it was not the cause of *this* crash — reported still reproducing afterward with the exact same signature, in the exact same `onError` lambda in `makeFolderListRequest` this time (full call stack captured, saved to `apicrash.txt` again), still *inside* the new `try`/`catch`. That "still not caught by try/catch" fact, now from the *same* line twice, pointed at a mechanism that bypasses C++ exception handling structurally, not just an unlucky assert — see the next entry.

### Fixed (2026-09-16, actual root cause: non-UTF-8 text reaching an implicitly-noexcept logger destructor)

With a full call stack in hand (`apicrash.txt`, `onError` in `makeFolderListRequest` again, still inside the try/catch added in the previous fix), traced the real mechanism: `asio::error_code::message()` (`ec.message()`, called to log the connection failure) returns OS error text via Windows' `FormatMessageA`, in the **system's ANSI codepage** — on this French-localized Windows machine, that's text like *"Aucune connexion n'a pu être établie..."*, containing accented characters, encoded as ANSI (e.g. CP1252), not UTF-8. That string is streamed into a temporary `cinder::log::Entry` via `CI_LOG_E`. When that temporary is destroyed at the end of the `CI_LOG_E(...)` statement — still lexically inside the `try` block — `Entry::~Entry()` (`Cinder/src/cinder/Log.cpp:185`, implicitly `noexcept` since no exception spec is given and no member throws) calls `writeToLog()` → `LogManager::write()` → every registered logger, including the always-on Windows Event Log logger (`LoggerSystem::ImplEventLog::write()`, `Log.cpp:438-439`), which unconditionally runs `std::wstring_convert<std::codecvt_utf8_utf16<wchar_t>>::from_bytes(text)` on it. `from_bytes` throws `std::range_error` when the input isn't valid UTF-8 — which ANSI-codepage accented text isn't. That exception then tries to escape `Entry::~Entry()`, an implicitly-`noexcept` destructor: per the C++ standard, an exception escaping a `noexcept` function calls `std::terminate()` **immediately**, without unwinding through (or being catchable by) any enclosing `try`/`catch` — including the one added in the previous fix pass. This explains every observed symptom: Debug-only was a red herring (the terminate() call is not Debug-specific; Release simply wasn't exercised against this exact "server unreachable + non-English Windows locale" combination), the try/catch appearing powerless was real and expected once the mechanism is understood, and the crash always pointing at the same `CI_LOG_E(ec.message() ...)` line was the correct clue all along — the earlier `<cctype>` UB was a real but unrelated bug found along the way.

Fixed at the call site (not in Cinder core, which per this file's own rule "shouldn't be modified"): added a small `sanitizeForLog()` helper at the top of `VDSession.cpp` that strips any byte ≥ 0x80 from a string (replacing with `?`), and applied it to `ec.message()` in all four `onError` lambdas before it reaches `CI_LOG_E` — plain ASCII is always valid UTF-8, so this guarantees the string can never trigger `from_bytes`'s throw, regardless of OS locale. `url->to_string()` was left unsanitized (it's pure ASCII protocol/host/path concatenation with no locale-dependent input in this code path — see `url.ipp`). Verified by rebuilding `Videodromm\VDRUIProject\vc2026\VDRUIProject.sln` Debug|x64 end to end (MSBuild, real compiler run) — zero errors, links clean.

**Confirmed fixed by the reporter**, running locally with the folder/shader API server stopped.

### Fixed (2026-09-16, VDAnimation::initLineIn() crash enumerating audio devices)

A separate, unrelated crash surfaced next (once the HTTP one above was actually fixed), same abort()/`_VCrtDbgReportW` presentation but a completely different call stack (`apicrash.txt` again): `videodromm::VDAnimation::initLineIn()` (`Cinder-VDR/src/VDAnimation.cpp:171`, `inputDevices = ci::audio::Device::getInputDevices();`) crashes with an access-violation *read* at `0xFFFFFFFFFFFFFFFF`, inside Cinder core: `Device::getInputDevices()` → `Device::getNumInputChannels()` → `shared_from_this()` → `std::_Ptr_base<Device>::_Construct_from_weak()` → `std::_Ref_count_base::_Incref_nz()`. That address pattern (`_Incref_nz` reading through a bad control-block pointer) is the signature of `shared_from_this()` being called on a `Device` whose `enable_shared_from_this` weak_ptr isn't validly wired up. Traced the construction path (`DeviceManager::addDevice()` in `Cinder/src/cinder/audio/Device.cpp` does `mDevices.push_back( DeviceRef( new Device( key ) ) )`, which is the textbook-correct way to wire up `enable_shared_from_this`) and the WASAPI enumeration path (`DeviceManagerWasapi::parseDevices()` in `Cinder/src/cinder/audio/msw/DeviceManagerWasapi.cpp`, guarded throughout by `CI_ASSERT(hr == S_OK)` on every COM call) without finding an obvious logic bug — this looks like a real, environment-dependent failure in Cinder's own WASAPI device enumeration on this machine (e.g. COM/audio-service state, a COM call failing past an assert that no-ops in this build) rather than a bug introduced by VDR/VDRUI code, and it wasn't fully root-caused.

This is already a known sharp edge in this codebase — note the existing `preventLineInCrash()`/`saveLineIn()` "poison pill" pattern (set `UseLineIn=false` *before* attempting line-in, only re-enable on success) and the comment already sitting right above this call: *"crashes if linein is present but disabled, doesn't go to catch block"*. That comment is exactly this bug: a raw SEH access violation is not a C++ exception, so the `try`/`catch(const std::exception&)` already wrapping this call (added by a previous author, further down in the same function) does nothing against it — same class of "try/catch is structurally powerless here" lesson as the HTTP fix above, just via a different mechanism (hardware AV vs. an exception escaping a `noexcept` destructor).

Fixed defensively, without touching Cinder core: added a Windows-only (`CINDER_MSW`) `safeGetAudioDevices()` helper in `VDAnimation.cpp` that wraps the two `ci::audio::Device::get{Input,Output}Devices()` calls in real structured exception handling (`__try`/`__except(EXCEPTION_EXECUTE_HANDLER)`), which *can* stop a raw AV from taking down the whole process (unlike C++ `try`/`catch`). MSVC forbids mixing `__try` with any C++ object requiring unwinding in the same function (error C2712) — including the `vector<DeviceRef>` temporaries from these very calls — so the actual work was split into a plain inner function (`doGetAudioDevices()`) called from the `__try` block, keeping `safeGetAudioDevices()`'s own body free of C++ objects; SEH scope still covers the whole call subtree, so the crash is still caught. `initLineIn()` now calls this wrapper on Windows and, on failure, logs and returns early (leaving `mUseLineIn` disabled for the session via the `preventLineInCrash()` call already ahead of it — mirroring exactly what the existing `catch` block already does on a normal exception). Mac (`CINDER_MAC`) keeps calling the two methods directly, unchanged, since `__try`/`__except` is an MSVC-only extension. Verified by rebuilding `Videodromm\VDRUIProject\vc2026\VDRUIProject.sln` Debug|x64 end to end (MSBuild, real compiler run — first attempt hit `EXCEPTION_EXECUTE_HANDLER` undeclared and the C2712 restriction described above, both fixed before this) — zero errors, links clean.

Not verified at runtime (same GUI-launch restriction noted elsewhere in this file) — run `VDRUIProject.exe` locally with `UseLineIn` enabled in `VDSettings.xml` and confirm the app now survives (logging "audio device enumeration crashed..." if the underlying WASAPI issue still reproduces) instead of aborting. ### Fixed (2026-09-16, scrub-slider jitter) + diagnostics added (video-texture blit fix didn't resolve it)

### Fixed (2026-09-16, actual root cause of "video plays audio only" found — missing DX/GL interop lock)

Reported again after the above: scrub jitter still not fixed, speed slider has no visible effect, video should reset to a basic shader on drop instead of keeping whatever effect shader was already on the fbo, and the video texture still never appears anywhere. Re-read `SetMediaInfo()`/`EndOpenURL()`/`OpenURL()` in `Cinder-WMFVideo/src/ciWMFVideoPlayerUtils.cpp` end to end to check the previous entry's timing theory — it's wrong: `SetMediaInfo()` runs synchronously inside `EndOpenURL()`, itself called synchronously from `OpenURL()` before it returns, so `mWidth`/`mHeight` (and therefore `mTex`/`hasTexture()`) are correctly populated by the time `ciWMFVideoPlayer::loadMovie()` reads them — that part was never the bug.

**Actual root cause, found by comparing against the vendored sample's own usage pattern**: `ciWMFVideoPlayer::draw()` wraps its `gl::draw(mTex, ...)` call in `mPlayer->mEVRPresenter->lockSharedTexture()`/`unlockSharedTexture()` (`PresentEngine::lockSharedTexture()` → `wglDXLockObjectsNV`, the WGL/DX interop handshake required before the GL side may safely read a DirectX-decoder-owned shared texture — `PresentEngine.cpp`). The blit code added in the "video texture-target mismatch" fix (two entries above) binds and samples `mVideo.getTexture()` directly, entirely bypassing `draw()` and therefore this lock/unlock pair. Without it, the GL texture object is never synchronized with the D3D surface the EVR presenter is actually decoding video frames into — it stays at whatever it was left at (uninitialized/black), while `hasTexture()`, `loadMovie()`, width/height, and the audio path are all completely unaffected, which is exactly why every diagnostic added previously (and the reporter's description) pointed at "everything reports success, image never appears." This also explains why the texture never made it into the shared pool as anything useful — `getFboTexture()`'s `MOVIE` case only assigns `mInputTextureList[0].texture` once `hasTexture()` is true, which it always was, so a (black) texture should have been registering; a black square in the Textures panel is easy to mistake for "the entry doesn't exist" (unconfirmed which of the two the reporter actually saw — the fix addresses both possible readings the same way).

Fixed: added `bool lockSharedTexture()`/`unlockSharedTexture()` to `ciWMFVideoPlayer` (`.h`/`.cpp`), forwarding to the same `mPlayer->mEVRPresenter` calls `draw()` already makes internally, and wrapped the blit in `VDFboShader.cpp`'s `getFboTexture()` `MOVIE` case with them (lock right before `rectTex->bind(0)`, unlock right after `rectTex->unbind(0)`).

**Speed slider "no visible effect" — separate, also found and fixed**: `ciWMFVideoPlayer::setSpeed()` (`IMFRateControl::SetPlaybackRate` under the hood) returns `false` on failure and logs to `cout` (invisible in a GUI app) — `MF_E_THINNING_UNSUPPORTED`/`MF_E_UNSUPPORTED_RATE` are common for non-1.0 rates unless thinning (dropping delta frames) is explicitly requested. `VDFboShader::setSpeed()` called it with `useThinning` defaulted to `false` and never checked the return value, so a silently-rejected rate change looked identical to a successfully-applied one. Fixed to retry with thinning enabled if the plain call fails, and log a one-shot warning (new `mVideoSpeedWarningLogged`) only if both attempts are rejected by the codec.

**Shader-reset-on-video-drop, per the new request ("I don't need effects in a shader for a video")**: dropping a video onto an existing fboshader kept whatever fragment shader that fbo already had (only the input texture was swapped) — reasonable for images (an effect shader is often exactly the point) but not for video, per the reporter. Fixed in `VDMix::loadTextureIntoFboActiveSlot()` (the function drag-and-drop actually calls) and, for consistency, in `VDMix::loadVideoFile()`'s existing-fbo branch: both now call `VDFboShader::loadFragmentShaderFromFile("inputImage.fs")` (the existing minimal shadertoy-style passthrough, already used elsewhere in this codebase, confirmed to have no uniform declarations of its own so it goes through `setFragmentShaderString()`'s "prepend the shadertoy.vd header" branch correctly) immediately before loading the video. Left open rather than guessing again — plausible now that the video actually renders: worth first confirming whether the *slider handle itself* visibly jumps during a drag (a real remaining UI bug) versus the *video image* stuttering/skipping during a seek (likely just `IMFMediaSession::SetPosition` being inherently asynchronous — seeks can take a few frames to settle, during which `getPosition()`/`getMaxFrame()` may read transitional values) — these need different fixes and were indistinguishable before the image was visible at all.

Verified by a clean MSBuild rebuild (Debug|x64), zero new warnings/errors from these changes. Not runtime-tested (same GUI-launch restriction) — this is the first fix in this whole video saga backed by a concrete, readable root cause (the missing `wglDXLockObjectsNV`/`wglDXUnlockObjectsNV` pair) rather than a diagnostic-and-guess cycle; still needs local confirmation that the video image now actually renders.

### Fixed (2026-09-16, video flip + three fbo-panel UI bugs left over from the shared-pool redesign)

### Fixed (2026-09-17, fbo mixing weights behaved as additive instead of opacity)

Reported: mixing multiple fboshaders together is wrong — each fbo's weight should act as an opacity from `0.0` (not displayed) to `1.0` (fully displayed), blending proportionally in between, without touching `post.glsl`/`fx.glsl`. Traced the actual compositing chain first, since neither `post.glsl` nor `fx.glsl` reference `iWeight`/multiple channels at all (both are single-`iChannel0` post-effect passes) — the real per-fbo weighted mix happens one stage earlier, in `mixette.glsl`: `VDSession::update()` calls `mVDMix->getMixetteTexture(0)` every frame (its return value is discarded at that call site, but the call's *side effect* — rendering the mixette shader and caching the result in `mMixetteTexture` — is what matters); `renderWarpsToFbo()` then draws that cached texture (via `getRenderedMixetteTexture()`, which just returns `mMixetteTexture` regardless of the index passed to it) onto each configured warp; the warped result feeds `renderPostToFbo()`/`renderFxToFbo()` as `iChannel0`, i.e. exactly the pipeline stage the report actually meant, just one shader upstream of where it was thought to be.

`mixette.glsl`'s default blend mode (`iBlendmode == 0`, the one actually in use) computed `c = Σ texture(iChannelN) * iWeightN` — a flat weighted **sum** across all 9 channels, not a proper opacity composite. That only behaves like "0 = hidden, 1 = fully shown" when at most one fbo has a nonzero weight at a time; with two or more active simultaneously, their full-brightness contributions add together (e.g. two fbos both at weight `1.0` produce a blown-out, additively-brightened image instead of one simply covering the other), which is the "wrong mixing" being reported.

**When this happened**: checked `git log`/`git log -p` on `Cinder-VDR/assets/mixette.glsl` — this formula has been there since the very first commit that added the file at all (before blend modes even existed: the original body *was* this weighted sum, unconditionally), and was carried forward unchanged when blend-mode switching was added later (`96602e9 blendmodes in mixette.glsl`, which wrapped the identical body in `case 0:`). It predates this entire session and everything else fixed above — nothing done here touched `mixette.glsl`, `post.glsl`, or `fx.glsl` before this point; the shape of the bug (additive instead of opacity-composited) is a long-standing characteristic of the shader, not a regression from any of the video/texture-pool work.

Fixed `case 0:` in every copy of `mixette.glsl` that's actually loaded at runtime or used for future Tinderbox generations (`assets/mixette.glsl` at the repo's shared top level, `Cinder-VDR/assets/`, `Cinder-VDRUI/assets/`, and both blocks' `templates/*/assets/mixette.glsl`) — replaced the flat sum with sequential "over" compositing, using each `iWeight` as that channel's own opacity against whatever the channels before it already produced: `c = vec3(0.0); c = mix(c, texture(iChannel0,uv).xyz, iWeight0); c = mix(c, texture(iChannel1,uv).xyz, iWeight1); ...` through `iChannel8`. This satisfies the request exactly: a single fbo at weight `1.0` fully replaces what's below it (`mix(x, layer, 1.0) == layer`), weight `0.0` contributes nothing (`mix(x, layer, 0.0) == x`), and values in between blend proportionally with the accumulated result of every layer below — `iChannel0` is the bottom of the stack, `iChannel8` the top.

Not runtime-tested (same GUI-launch restriction) — these are plain-text GLSL assets, not compiled by MSBuild, so no rebuild was needed/run for this change. Worth confirming locally: two or more fbos active at once no longer wash out/over-brighten, and a single fbo's weight slider now behaves as a clean 0-1 fade rather than a brightness multiplier stacked additively with whatever else is on.

### Fixed (2026-09-17, MIDI still showed no devices after the caching fix — actual root cause: RtMidi silently compiled as a non-functional dummy backend)

Reported again after the caching/duplicate-filter fix above, with the log attached: `midiSetup: setupMidi` immediately followed by `no midi in ports found` `no midi out Ports found` — both in **and** out reporting zero. That "out" is also empty is the key new fact: `cinder::midi::MidiOut::getNumPorts()` was never subject to the caching bug (it already queried live), and Windows always exposes at least one MIDI *output* port out of the box (the built-in "Microsoft GS Wavetable Synth" software synth) — for a real, working RtMidi backend to report zero *output* ports on Windows regardless of what's plugged in is close to impossible. That pointed away from "stale snapshot" or "nothing connected" entirely and toward the RtMidi backend itself never talking to a real OS API.

Confirmed by reading `Cinder-MIDI2/lib/RtMidi.h`'s own platform-detection block (~line 571): `#if defined(CINDER_LINUX) #define __LINUX_ALSASEQ__ #elif defined(CINDER_MSW) #define __WINDOWS_MM__ #elif defined(CINDER_MAC) #define __MACOSX_CORE__ #endif`, followed immediately by `#if !defined(__LINUX_ALSA__) && !defined(__UNIX_JACK__) && !defined(__MACOSX_CORE__) && !defined(__WINDOWS_MM__) #define __RTMIDI_DUMMY__ #endif` — `RTMIDI_DUMMY` is documented in the same file as "a compilable but non-functional API" (always reports 0 ports, does nothing). This block depends on `CINDER_MSW` (defined by `cinder/Cinder.h`) already being defined by the time it runs — but `RtMidi.h` never included that header itself, only relying on *whichever translation unit happened to include it first* to have already pulled in a Cinder header. **`Cinder-MIDI2/lib/RtMidi.cpp` — the file that actually implements `RtMidiIn`/`RtMidiOut`, i.e. the object code that ends up in the app regardless of what any other file sees — starts with a bare `#include "RtMidi.h"` and nothing else before it** (confirmed by reading its first 40 lines), so in *that* translation unit `CINDER_MSW` was never defined, none of the three real backends got selected, and the entire compiled RtMidi implementation silently fell back to `__RTMIDI_DUMMY__` — a fully valid, zero-warning compile that simply never queries Windows for anything. (Some other files, like `VDMidi.h`, do include `cinder/Cinder.h` before pulling in MIDI headers, and `RtMidi.h`'s `RtMidiIn`/`RtMidiOut` wrapper methods are `inline` — defined per translation unit — so which backend a given TU thinks it's using could actually have differed across files, an ODR violation on top of everything else; moot now that every TU is guaranteed to agree.)

Fixed at the single, correct root: added `#include "cinder/Cinder.h"` directly inside `RtMidi.h`, immediately before its own platform-detection block, so `CINDER_MSW`/`CINDER_LINUX`/`CINDER_MAC` are guaranteed defined by the time that check runs in *every* translation unit that includes `RtMidi.h`, regardless of what else that file happened to include first. This is a one-line, header-only fix in a file this project's own `README.md` already documents needing manual preprocessor setup for (`"add __WINDOWS_MM__ to preprocessor"`, `Cinder-MIDI2/README.md:42`) — i.e. this exact class of "the platform macro isn't visible where it's needed" gap was a known sharp edge in this block, just not one anyone had hit before because nothing in this codebase previously depended on RtMidi actually enumerating anything.

This supersedes neither of the two bugs fixed in the previous entry — the stale port-count cache and the `listPorts()` duplication were both real and are still worth having fixed — but neither could have mattered while the underlying backend was the dummy API the whole time; this was the actual blocker matching every symptom reported (0 devices, both directions, unconditionally, with or without hardware attached).

Verified by a clean MSBuild rebuild (Debug|x64, forces a recompile of `RtMidi.cpp`/`MidiIn.cpp`/`MidiOut.cpp`/`VDMidi.cpp` since a shared header changed), zero new errors/warnings. Not runtime-tested (same GUI-launch restriction) — worth confirming locally: even with nothing plugged in, MIDI **out** should now list at least "Microsoft GS Wavetable Synth" (or equivalent) — if it still shows zero after this fix, something else is wrong (e.g. verify the rebuilt exe was actually relaunched, not a stale one).

### Fixed (2026-09-17, MIDI messages never arrive — RtMidi's own open/driver errors were entirely invisible)

Reported back: `MidiInCallback: N bytes` never appears at all — confirming the break is below the app's own signal wiring, inside RtMidi/Windows itself, exactly as the diagnostic in the previous entry was designed to establish.

Root cause: `MidiApi::error()` (`RtMidi.cpp:248-278`) is RtMidi's single error-reporting path. With no error callback registered (the state this codebase was in until now), most of the realistic failure types — critically `RtMidiError::DRIVER_ERROR`, which is exactly what `MidiInWinMM::openPort()` (`RtMidi.cpp:2074-2144`) reports if `midiInOpen`/`midiInPrepareHeader`/`midiInAddBuffer`/`midiInStart` fail for any reason (the device already claimed by another application is the single most common real-world cause) — write only to `std::cerr` and **do not throw**. In a windowed (non-console) app `std::cerr` goes nowhere anyone can see, and since it doesn't throw either, `Input::openPort()`'s caller has no way to detect the failure: `MidiInWinMM::openPort()` returns early without ever calling `midiInStart()`, so RtMidi's OS-level callback is never registered and `MidiInCallback` can never fire — while `VDMidi::openMidiInPort()` (`VDMidi.cpp:142`, pre-existing) set `mMidiInputs[i].isConnected = true` **unconditionally**, regardless of whether the open actually succeeded. Net result: the UI confidently showed "connected," nothing crashed, nothing logged anywhere, and no message could ever arrive — a completely silent failure mode with zero trace, until deliberately instrumented.

Fixed by registering a real error callback: `RtMidiErrorLogCallback` (`Cinder-MIDI2/include/MidiIn.h` declaration, `src/MidiIn.cpp` definition + wired via `mMidiIn->setErrorCallback(&RtMidiErrorLogCallback, this)` in `Input`'s constructor) routes every RtMidi-internal error into `CI_LOG_E`, finally making the actual reason (e.g. "error creating Windows MM MIDI input port") visible in this app's own log file instead of a discarded `std::cerr` write. Registering *any* error callback also changes RtMidi's own behavior for the better as a side effect: `MidiApi::error()`'s very first check is `if (errorCallback_) { ...call it...; return; }`, bypassing the `throw` at the bottom entirely — so the two error types that previously *did* throw uncaught (`NO_DEVICES_FOUND`, `INVALID_PARAMETER`, e.g. from a stale/out-of-range port index) now log instead of potentially crashing the app.

Also closed the "confidently wrong" UI gap this exposed: added `Input::hadOpenError()` (a flag reset at the top of every `openPort()` call, set by the new error callback if RtMidi reports anything during it) and changed `VDMidi::openMidiInPort()` to only set `isConnected = true` when `!hadOpenError()` — the "Connect" button (and the auto-connect-by-preferred-device-name path in `midiSetup()`, which calls the same function) now honestly reflects whether the port actually opened.

Verified by a clean MSBuild rebuild (Debug|x64), zero new warnings/errors. Not runtime-tested (same GUI-launch restriction) — worth confirming locally: connecting a device that's free should now actually deliver messages (both `MidiInCallback:` and `midiListener:` log lines should appear); connecting one that's busy/claimed elsewhere should now show a `RtMidi error (type ...): ...` log line and the UI should say "Connect" was NOT successful, instead of silently doing nothing forever.

### Fixed (2026-09-17, mixette occlusion + sequence status text frozen)

Two bugs reported from a test setup ("particlez", a `mix.json` loading a deliberate mix of sequence/video/shader-with-image fbos together):

**"the fboshader is rendered only if other fboshaders iweight* are 0.0"** — a direct, foreseeable consequence of the *previous* mixette fix in this file (2026-09-17, "fbo mixing weights behaved as additive instead of opacity"): switching to sequential Photoshop-style "over" compositing gave a single fbo's weight the right 0-1 opacity meaning, but it also means any *higher-indexed* fbo sitting at weight 1.0 (the default weight value, per `VDUniforms.cpp`) completely replaces every layer stacked below it — so with several fbos all at their default weight, only the highest-indexed one was ever visible, exactly matching "only if other fboshaders iweight* are 0.0". Applied to all five copies of the file (repeating the same convention as every earlier mixette/mixing fix this session).

**Sequence status text frozen at "0/522 loaded in ...ms"** — root-caused to an interaction with this session's *own* earlier sequence-playback-controls work: `VDFboShader.cpp`'s `SEQUENCE` case only ever updated `mFboStatus` (the string this exact panel displays) inside the `!mSequenceManualControl` branch's `mPreloadTextures` block. The images kept loading and advancing correctly the whole time (via the separate `mSequenceAccumulator`/`loadNextTexture()` logic in the manual-control branch) — only the status *text* was stale, matching "always shows 0/522 ... although images are loaded" exactly. ### Fixed (2026-09-17, mixette normalization dimmed the mix + possibly explains "fbo 0 only renders if others are 0")

Reported back after the normalized-average fix above: fbo index 0 specifically still exhibited the old "only renders if others are 0.0" symptom, while other fbo combinations blended together fine but the overall mix wasn't bright enough.

Re-examined `VDMix::getMixetteTexture()`'s C++ binding/uniform-upload loop — nothing in it treats index 0 differently from any other index, so there's no code-level special-casing to explain a strictly-index-0 bug there. The more likely explanation: `iWeight0` defaults to `1.0` while `iWeight1..iWeight8` all default to `0.0` (`VDUniforms.cpp`) — fbo 0 is the "always-on base layer" by convention, everything else starts off. Under the *previous* fix's normalized-average formula (`sum / max(totalWeight, 1.0)`), turning other fbos on grows `totalWeight` without growing fbo 0's own weight, so fbo 0's *share* of the result shrinks the more layers are active — dimming, not literal occlusion, but dim enough to read as "gone" once several other layers are active, which also directly explains the separate "not enough brightness" complaint (the same division was dimming every layer, not just fbo 0).

Fixed by dropping normalization entirely: `mixette.glsl`'s `case 0:` is now a plain weighted sum, `clamp()`-ed to `[0,1]` only at the very end. Each layer contributes its own full, un-dimmed brightness (weight 0 = invisible, weight 1 = full brightness, independent of anything else); only the *combined* result clips to white where several bright layers genuinely overlap, the same way ordinary additive mixing/exposure clipping works, instead of the whole frame being scaled down as a function of how many layers happen to be active. Applied to all five copies of the file, same as every earlier mixette pass this session.

Also added a throttled diagnostic (`VDMix::getMixetteTexture()`, ~once every 120 calls) logging each fbo's `isValid()`/weight state, in case this brightness-based explanation turns out not to be the whole story for the reported "fbo 0" symptom — if it recurs, the log will show directly whether fbo 0's own validity/weight data is actually wrong (a real, separate bug) rather than requiring another guess-and-check round on the shader formula.

Not runtime-tested (same GUI-launch restriction) — worth confirming locally: fbo 0 stays visible at its own brightness regardless of how many other fbos are also active, and the overall mix is no longer dimmer than expected with multiple active layers. ### Fixed (2026-09-17, actual root cause of "fbo 0 disappears" — a texture-unit clobber, not a shader/brightness issue)

The throttled diagnostic added in the previous entry gave a clean answer: across every logged frame, fbo 0 was `isValid=1 w=1` — always correct. So the C++ state feeding the shader was never wrong, which meant the clamped-additive shader fix, while a real improvement, was never going to fix *this* particular symptom — it was misdiagnosed as a shader/brightness problem. The actual bug was one level up, in `VDMix::getMixetteTexture()`'s C++ binding loop.

Root cause: `VDFboShader::getTexture()` (`VDFboShader.cpp:809-819`) doesn't just return a cached texture — it unconditionally calls `getFboTexture()` every time, which **re-renders that fbo's own shader as a side effect**, and that render binds *that fbo's own input texture* to GL texture unit 0 internally (the standard single-input-texture convention used throughout this codebase). The old binding loop did `mFboShaderList[i]->getTexture()->bind(i)` **inside the same loop, one fbo at a time** — so for fbo 0 (i=0): render fbo 0 (as a side effect, binds fbo 0's *input* to unit 0), then bind fbo 0's *output* to unit 0 for the mixette pass. So far correct. But then for fbo 1 (i=1): render fbo 1 (which, as *its own* side effect, rebinds unit 0 to *fbo 1's own input texture* — completely unrelated to the mixette pass, just an artifact of how every fbo renders itself) — silently clobbering fbo 0's binding before the mixette shader ever runs. By the time `gl::drawSolidRect()` actually executes `mixette.glsl`, `iChannel0` was sampling whatever the *last* fbo to render internally left on unit 0, not fbo 0's output at all. This exactly explains the report: fbo 0, always first in the loop, was clobbered by every fbo that rendered after it; whichever fbo happened to render *last* in a given frame was never itself clobbered, hence "others mix well."

Fixed by splitting the loop in two: first, iterate every valid+active fbo and call `getTexture()` to trigger all rendering up front, collecting each result in a `std::vector<Texture2dRef>` **without binding anything yet**; only after every fbo that needs to render has already done so, iterate that vector and bind each result to its mixette channel. No render can clobber unit 0 partway through anymore, since no binding happens until every side-effecting render has already completed.

This means the two mixette.glsl fixes earlier in this session (normalized-average, then clamped-additive) were both real, reasonable improvements to the compositing *model* (0=invisible/1=full-brightness semantics, avoiding blowout), but neither was the actual cause of the reported "fbo 0 disappears" symptom — that was a pure C++-side GL-state ordering bug, unrelated to which blend formula the shader used. Left the clamped-additive shader model in place (still the right choice for "each layer's own independent brightness" semantics) since it was never the bug — this fix is layered on top of it, not a replacement.

Verified by a clean MSBuild rebuild (Debug|x64), zero new warnings/errors beyond pre-existing ones. Not runtime-tested (same GUI-launch restriction) — worth confirming locally: fbo 0 now stays visible with any combination of other fbos also active, at the brightness the clamped-additive shader model implies. The throttled `getMixetteTexture fbo states:` diagnostic is left in place in case a similar-looking report ever recurs for a genuinely different reason.

### Added (2026-10-05, projector output window + Spout backup player)

Goal: for live shows, render to the projector(s) straight from the Cinder app, keeping Resolume as an optional backup/video player. Chosen architecture, after comparing it with two apps linked by websockets/Spout/NDI:
- **One app, two windows** for performance. Cinder shares GL textures between windows (`AppImplMswBasic::createWindow` → `findSharedRenderer` → `wglShareLists`), so the projector window draws the textures the main window already rendered, with no copy and no extra latency.
- **A Spout player app as a show-time safety net**, so a crash of the main app can't put the Windows desktop or an error dialog on the projector.
- **No NDI between two apps on the same PC:** GPU→CPU readback, compression, 1–3 frames of latency. **Websockets carry control data only**, never video.

**`VDOutputWindow`** (new, `Cinder-VDRUI/include|src/VDOutputWindow.*`, owned by `VDUI`, reached via `mVDUI->getOutputWindow()`), opened from a new **"Output"** toolbar button/panel in `VDUI.cpp`. The button turns green while the window is open:
- **Displays:** a borderless window spanning the union of the selected displays, so several projectors side by side give one window 2x (or more) wide. A warning shows when the selection isn't one rectangle. On Windows the exact physical-pixel rect is applied with `SetWindowPos`, since `Display::getBounds()` is in pixels while `Format::size()` is in points with high density enabled. Focus goes back to the UI window.
- **Content "Main view":** the same texture the main window shows (Post/Fx/Warp/fbo display mode), stretched. The apps' `draw()` now chooses one texture and calls `setMainViewTexture(tex)`. The 4 duplicated per-mode draw/send blocks were merged into one.
- **Content "Warps (projection mapping)":** Cinder-Warping meshes rendered at the output's own resolution, via the new `VDSession::drawWarpsToCurrentTarget(composite)`. That draws all warps into any bound framebuffer with fbo-sized logical matrices, the same scaling trick as `getWarpPreviewTexture()`. Warps without a specific fbo can show the Mix, Post (default) or Fx. Post/Fx sample the mixette directly now, so this is no longer the circular dependency `resolveWarpInputTexture()`'s old comment describes. Fx is only re-rendered every frame while the display mode is Fx. Use one warp per projector for a multi-projector span. Mouse events on the output window are rescaled to fbo space (`toWarpSpace()`) and forwarded to the warp editor, so control points can be dragged on the actual projection (`W` toggles edit mode, as before).
- **Important GL detail:** the warp content is rendered into an output-sized Fbo from **the main window's context** (in `update()`), and the output window only blits that texture. Cinder `Batch` VAOs belong to the context that created them (`Vao::mCtx`), while textures are shared. Drawing the warp meshes from the output window's own context would have used foreign VAO names. Creating or closing a window makes its context current, so open/close are deferred requests handled in `update()`, and the main context is restored right after.
- **Pacing, "Pace by projector vsync" (default on):** vsync on the output window only, off on the main window, and Cinder's frame-rate timer disabled while the output is open. One blocking swap per frame then drives the loop. With two vsynced swaps per frame, the frame rate can drop to half. Everything is restored on close.
- **Safety:** Esc on the output window closes it, and `f` is ignored there (it would toggle the output window's own fullscreen). The window closes itself if its displays disappear (checked every 60 frames). If the main window is closed while the output is open, the app quits instead of running headless. `resize()` only re-seeds ImGui for the main window.
- **Persistence:** settings go to `assets/output.json` (content, composite, pacing, always-on-top, and selected displays stored by desktop bounds, which are stable across runs unlike indices). On first run, every display except the main one is selected.
- **Spout to Resolume (and VDCode/NDI) is untouched** and keeps running in both modes.
- Wired into `VDRUIProject`, the VDRUI Tinderbox template (`_TBOX_PREFIX_App.cpp`, so future projects get it) and `VDSpoutInNdiOut`. `VDOutputWindow.cpp/.h` were hand-added to both existing vcxproj/filters; new Tinderbox projects pick them up through `src/*.cpp`.

**`VDSpoutInNdiOut` as the backup Spout player:**
- **`n` key:** toggles an NDI sender, **off by default**. The `CinderNDISender` is now a `std::unique_ptr`, created on enable and destroyed on disable, so it isn't advertised on the network while off. The readback only happens when it's on *and* a receiver is connected. The title shows the sender name and NDI state.
- **Fixed in the same pass:** `update()` used to read the frame back and send NDI every frame unconditionally, dereferencing a null `mSurface` before any Spout sender was received. It also allocated a throwaway texture every frame, and NDI was sent a second time from `draw()`.
- **Sender picker:** `SelectSenderPanel()` (SpoutPanel) opens on right-click only, and not over an ImGui panel (`WantCaptureMouse`). It used to open on every mouse click, UI clicks included (2026-10-07).
- **What it shows:** the received Spout frame when there is one, otherwise its own render. It can also use the output window to span several projectors.

Verified: MSBuild Debug|x64 + Release|x64 of `VDRUIProject` and `VDSpoutInNdiOut`, zero errors. Not runtime-tested (exe launch forbidden on this PC).

### Added (2026-10-07, MIDI learn shared with TSWebsocketServer)
